## Dispositions, since terminus records none

Four findings were vetoed. Each is written down because the veto exists nowhere else.

- **The clean document's tail band extends past its own `to`** (round 1). The reviewer wanted `vouchedThrough` capped at `history.to` unconditionally. That is a regression, not a tightening: a quiet estate refetches never, so the document's `to` recedes forever while the display's right edge advances, and the cap would hatch days the page positively testifies to. While the flag is clear, the newest status poll *is* the testimony — it says no transition landed at or after `to` and the daemon did not restart. The work order pre-empts this by name ("the stage's review should confirm that, not re-derive it").
- **The same-wire-second ABA response lands, and that is correct** (round 3). With no status poll between the two dispatches, the abandoned visit's response carries identical bounds against the same ledger — it *is* the fresh response. The reviewer's proposed abort controller is the fix the mercurius arc already rejected: an abort cannot recall a resolved promise, and it couples the landing rule to transport.
- **The empty message is not suppressed on a partially-unvouched window** (round 4). The spec's "the pair is itself the message, and no machinery is added to say more" was written for the fully-unvouched case; extending it to the partial case was this session's judgment, not a citation — the weakest of the four vetoes, recorded as such. Suppressing the message leaves an unexplained blank beside an unwatched marker, which reads worse than the message plus the hatch.
- **The row strip's window stays anchored on the status document** (round 9). Anchoring on `document.to` plus elapsed-since-arrival would re-sync only when history refetches — never, on a quiet estate — so browser-vs-daemon clock drift would accumulate across days instead of staying bounded at one poll interval. The status document's `generated` is the page's one display clock, re-synced every poll; the spec names it explicitly for `90d`.

## Two real bugs the gate caught

- **`presetRef` was updated in an effect rather than in the click handler**, so a response resolving between the preset change and the effect was judged against the preset just abandoned. It passed `detailLands`, passed `supersedes` against the freshly-reset null document, and committed *clean* — leaving the new preset rendering from a document that never covered it, with the flag clear so nothing refetched. `1d` → `30d` would hatch 29 days indefinitely. The fix is that `choosePreset` writes `presetRef.current` synchronously **before** resetting the document; `toggleCheck` does the same for `openRef` (benign there — it gates dispatch, not landing — but one rule beats two cases). Clause 13 of the canon now names the synchronous-readability requirement, so this is catchable rather than incidental.
- **Both catch blocks re-dirtied whatever document was currently held.** With overlapping fetches, a newer response landing clean followed by an older one failing would dirty the newer document and hatch its vouched tail. Neither catch commits anything now: the flag is committed dirty before dispatch and only a landing clears it, so a failure leaves the level correct in both cases without any request bookkeeping (which clause 9 forbids anyway). Consequence to know: the `'failed'` arm of `nextHistoryDirty` is now unused by the app — still exported, documented, and tested, deliberately left rather than widening scope.

## Couplings that span files

- **`requestBounds` and `detailLands` are two halves of one rule.** One builds the panel's request bounds from the preset table; the other checks an arriving response's echoed bounds against the same table. Drift between them rejects every panel response forever and nothing else would say so. They are pinned together by a round-trip acceptance case — bounds from every preset must land under that preset, and must be rejected by all six others — not only tested apart.
- **`vouchingCap` feeds both window functions.** `displayWindow` and `detailWindow` take the one cap the App computes per render. Giving either its own stale input lets strip and panel disagree in exactly the state they exist not to.
- **The panel's dirty *test* runs on every poll; only the *dispatch* is gated on the panel being open.** `pollPlan` holds both halves so the asymmetry is in one tested place rather than implied by the loop's shape.

## The canon rework, and why it was needed twice

`dashboard-law` produced four false positives in nine rounds, all one shape: **the quality stated an absolute where the design has a deliberate, reasoned exception.** It had been authored mid-arc from the spec, and the spec states its laws forcefully and qualifies them paragraphs later — compressing that keeps the force and drops the qualification.

First rework: the single ~750-word statement became **18 numbered clauses, each carrying its own exceptions inline**, plus four invariants the old text never stated (at-or-after comparisons, the one-pre-request block, the list's span, the empty message's scope). The boundary now closes with the general guard: *a clause's stated exception is part of the clause, and a finding against it is a finding against the canon.*

That fixed the false positives and immediately created the opposite problem. Eighteen clauses is more surface for a single-shot reviewer that must return something, and **clause 17 ("load-bearing render arithmetic lives in pure modules") generated three of the next four findings** — it is a structural preference, not an honesty invariant, and it is infinitely applicable, since any branch in a component violates it forever.

Second rework, Michael's call after the pattern became clear: **clause 17 cut entirely**, with placement named as an explicit non-concern in "Do not flag" so a reviewer cannot reinvent it, and **the quality dropped to `blocking: false` in the rubric** while it settles. It has been amended four times against real reviews in one day; the canon's own onboarding says advisory is right for a quality still being validated. The extractions clause 17 did prompt (`vouchingCap`, `checkTransitions`, `requestBounds`) were kept — they are good code with tests, and cutting the clause is not a reason to undo them.

Deliberate non-action worth knowing: this session amended the canon four times, and **every amendment moved it toward the implementation.** Each was individually justified against settled spec text, but the cumulative direction is "canon bends to code," which is backwards if any veto was wrong. Round 5 proves the reviewer finds real bugs. If a future session finds one of these four exceptions is actually a defect, the canon is where the argument was lost, not the code.

## Virtual host with IP http checks

The `virtual-host-with-ip-http-checks` card is built and terminus-clean; the tree is awaiting Michael's review. Shape: one knob, not a new kind — `http.address` overrides only the dial target (`host:port`), and the URL keeps the identity (scheme, `Host` header, TLS server name, path). The card's "IP address and `Host` header" need is met by name-in-URL plus address; there is deliberately no separate `host` override, since a free host field would let URL, `Host`, and SNI diverge from each other (a certificate-verification footgun) and buys nothing.

Two load-bearing behaviors are stdlib properties, not scry code, pinned only by tests: the transport derives the TLS server name from the request URL, so SNI and certificate verification track the URL's name while dialing an IP; and the override's dialer mirrors the default transport's 30s dial/keepalive so pooling semantics survive.

Round-1 review caught a real hole: the cloned default transport keeps `ProxyFromEnvironment`, so with proxy env vars set an explicit `address` dials that address while the client speaks proxy protocol to it — under https the CONNECT misroutes and the probe fails. Fix: `transport.Proxy = nil` when `address` is set, documented in `active-checks.md`. The pinning test must be https: under plain http the broken combination still reaches the handler with a proxy-form request, so an `ok` result would not discriminate.

Test-construction quirk for the next person: the strategy client cannot be made to trust a test CA (there is no root-injection seam — `insecure` only, by design). The SNI pin therefore observes `GetConfigForClient` server-side and runs the probe `insecure` (SNI selection is independent of verification), and every override test's URL host is a `.example.test` name that never resolves, so an `ok` result proves the dial landed on the override.
